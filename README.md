# Prompt2Play

Type one sentence. An AI designs a 6x6 puzzle level. You publish it as a Solana account you own. Anyone can solve it, and the program replays their moves on-chain before it counts.

Devnet only. This is a hackathon build, not an audited product.

## The game

- Grid 6x6. Cells: floor, wall, key, exit. Up to 3 keys.
- Walk one cell per move (up, down, left, right). Walls and the grid edge block you, but a blocked move still costs a move.
- The exit is locked until every key is collected. Keys are picked up by standing on them.
- Every level has a move cap (at most 40). The generator sets it to the shortest solution plus 4.

## How Solana is used

- **Level account** (PDA `["level", creator, level_id u64]`): creator, title, prompt, the 36 cells, start, move cap, best moves, best solver, plays, solves, creator tip, creation slot. The creator's wallet owns the namespace; the level is public state anyone can read with `getProgramAccounts`.
- **Run account** (PDA `["run", level, player]`): the player's best solution, packed 2 bits per move.
- **`publish_level`** validates on-chain: cell values, exactly one exit, at most 3 keys, start not on a wall or the exit, move cap 1..=40, title <= 48 and prompt <= 120 bytes, tip <= 0.01 SOL. It also flood-fills from the start so every key and the exit are reachable. It does not prove the cap is achievable.
- **`submit_run(moves)`** replays the moves inside the program. It requires all keys to be collected, then the exit to be entered on the last move, within the cap. The first valid solve per player increments `solves` and transfers the creator's tip from solver to creator. Later runs by the same player are accepted only if strictly shorter; otherwise the transaction fails with `NotBetter`. `best_moves` and `best_solver` change only for a strictly shorter run.
- `plays` counts accepted runs. Invalid runs revert, so they are not counted. `best_moves = 0` means unsolved.

Move codes on the wire: 0 = U, 1 = D, 2 = L, 3 = R.

## Architecture

```
programs/prompt2play/   Anchor program
  src/engine.rs         pure rules: validate_level, replay, move packing (no Anchor types)
  src/lib.rs            accounts and the two instructions
  tests/integration.rs  LiteSVM tests against the built .so
fixtures/replay.json    25 shared cases (generated by fixtures/gen.mjs)
shared/engine.ts        TypeScript reference of engine.rs, plus BFS solver
shared/chain.ts         hand-written client for the program (instructions, account decoding)
server/                 Express level generator (OpenRouter LLM, validated, procedural fallback)
web/                    Vite + React + TypeScript client
scripts/                deploy-and-seed.sh, seed.mts, list.mts
```

Rust/TS parity: `engine.rs` and `shared/engine.ts` are both run against `fixtures/replay.json`, so the on-chain rules and the client rules cannot drift silently.

Level generation (`POST /api/generate` with `{"sentence": "..."}`): the server asks an LLM (`GEN_MODEL`, default `anthropic/claude-haiku-4.5`) for a level with a strict JSON schema, then validates it and solves it with BFS. It retries up to 4 times, feeding validation errors back to the model as repair hints, then falls back to a deterministic procedural generator seeded by a hash of the sentence, so a request always returns a level: `{title, cells, start, move_cap, optimal_moves, source}` where `source` is `"llm"` or `"procedural"`. Without `OPENROUTER_API_KEY` it uses the procedural generator only. The browser checks the level again with its own BFS before publishing.

## Run it

Requirements: Rust, Solana CLI, Anchor CLI 1.1.x, Node 20+.

```
anchor build
cargo test                 # engine unit tests + LiteSVM integration tests (needs anchor build first)
npm install
npm test                   # TS parity tests, generator tests, client encoding tests
npm run typecheck
npm run build              # web production build
```

Dev servers:

```
OPENROUTER_API_KEY=...  npm run server    # level server on :8787 (key optional)
npm run web                               # Vite dev server, proxies /api to :8787
```

Environment variables:

| Variable | Used by | Meaning |
| --- | --- | --- |
| `OPENROUTER_API_KEY` | server | enables LLM generation; never logged |
| `GEN_MODEL` | server | model id, default `anthropic/claude-haiku-4.5` |
| `PORT`, `CORS_ORIGIN` | server | listen port (8787) and allowed origin (`*`) |
| `VITE_RPC` | web | RPC URL, default devnet |
| `VITE_PROGRAM_ID` | web | program id if you deployed your own |
| `VITE_API_URL` | web | base URL of the level server if it is not proxied |

Deploy and seed on devnet:

```
scripts/deploy-and-seed.sh <payer-keypair.json> <program-keypair.json> [rpc-url]
```

The payer pays for the deploy and owns three seed levels, each published and then solved with its BFS-shortest solution. If the program keypair's public key differs from the id compiled in, the script updates `declare_id!`, `Anchor.toml` and `shared/chain.ts`, then rebuilds. The script refuses RPC URLs that are not devnet or localhost. Keypairs are yours to supply; nothing in this repo contains one (`.keys/` is gitignored).

## Known limits

- `move_cap` is trusted from the creator; the program checks shape and reachability, not that the cap is feasible. The web client and server only publish levels they solved.
- Anyone can publish a level; there is no moderation.
- Wallet support is Phantom only.
